# MySQL 高频面试题（SQL优化、索引、事务、锁机制）

## 一、索引面试题

### 1. 什么是索引？底层原理？
索引是加速数据库查询的磁盘数据结构，MySQL InnoDB 索引底层是 **B+树**。
特点：
- 非叶子节点只存索引键，叶子节点存完整数据/主键；
- 叶子节点采用双向链表，范围查询效率高；
- 树高度低，磁盘IO次数少，查询性能优异。

### 2. 为什么用 B+树 不用 B树/哈希/二叉树？
- 二叉树：树层高，磁盘IO多，不适合大数据量；
- B树：非叶子节点也存储数据，单页存放索引少，层高更高；
- 哈希索引：不支持范围查询、排序、前缀模糊匹配；
- B+树：层高低、范围查询快、叶子节点有序链表结构，适配磁盘分页存储。

### 3. 聚簇索引 和 非聚簇索引 区别
- **聚簇索引**：主键即索引，叶子节点存储整行数据，一张表仅有一个；
- **非聚簇索引（二级索引）**：叶子节点存储主键值，查到主键后需回表查询完整数据。

### 4. 什么是回表？什么是覆盖索引？
- 回表：通过二级索引查询到主键，再通过聚簇索引查询整行数据的过程；
- 覆盖索引：查询所需字段全部包含在二级索引中，无需回表查询，性能最优。

### 5. 最左前缀原则？
联合索引 `(a,b,c)` 匹配规则：
- 可命中场景：仅 `a`、`a+b`、`a+b+c`；
- 失效场景：单独 `b`、`c`、`b+c`；
核心：索引从左向右依次匹配，跳过前置字段，后续索引全部失效。

### 6. 索引失效的常见场景
1. 前置模糊查询 `%xxx`、`%xxx%`；
2. 索引列参与运算、调用函数、发生隐式类型转换；
3. `or` 两侧字段未同时建立索引；
4. 违反最左前缀匹配原则；
5. 使用 `not in`、`!=`、`is not null` 等查询；
6. 数据库优化器放弃索引选择全表扫描。

### 7. 哪些字段不适合建索引？
- 低基数字段：如性别、状态等重复值极多的字段；
- 频繁更新的字段：索引需要同步维护，增加写入开销；
- 大文本字段：占用空间大，索引效率低；
- 极少作为查询条件的字段。

### 8. 联合索引怎么设计？
核心原则：**等值查询字段放前面，范围查询字段放后面，高频查询字段优先**。

## 二、SQL 优化面试题

### 1. SQL 优化整体思路
1. 使用 `explain` 分析执行计划，定位慢查询瓶颈；
2. 合理设计索引，避免索引失效场景；
3. 减少大表全表扫描，拆分大事务；
4. 优先使用覆盖索引，减少回表次数；
5. 优化分页、联表查询、子查询语句。

### 2. explain 关键字段含义
- `type`：访问类型，优先级：`eq_ref > ref > range > all`，`all` 代表全表扫描，性能最差；
- `key`：SQL 实际命中使用的索引；
- `rows`：预估扫描的数据行数，数值越小性能越好；
- `Extra`：额外信息，出现 `Using filesort`、`Using temporary` 需重点优化。

### 3. 什么是 Using filesort、Using temporary？
- Using filesort：未通过索引完成排序，触发文件级排序，性能损耗大；
- Using temporary：查询过程用到临时表，常见于 `group by`、多表联表场景，通常需优化索引。

### 4. 大分页 limit 100000,10 怎么优化？
1. 主键游标优化：`where id > 100000 limit 10`；
2. 延迟关联：先查询分页主键，再关联查询完整数据；
3. 业务层优化：禁止深分页，采用游标分页替代传统分页。

### 5. join 优化原则
- 小表驱动大表，减少循环匹配次数；
- 联表关联字段必须建立索引；
- 严格限制关联条件，避免产生笛卡尔积。

### 6. 为什么禁止 select * ？
- 查询多余无用字段，增加网络IO和磁盘IO；
- 无法使用覆盖索引，必然触发回表；
- 表结构新增字段后，易引发业务逻辑异常。

## 三、事务面试题

### 1. 事务四大特性 ACID
- **原子性**：事务内操作要么全部成功，要么全部回滚；
- **一致性**：事务执行前后，数据库数据完整性约束保持一致；
- **隔离性**：并发事务之间相互隔离，互不干扰；
- **持久性**：事务提交后数据永久落地，服务器崩溃数据不丢失。

### 2. MySQL 四大隔离级别 & 对应问题
1. 读未提交：存在脏读、不可重复读、幻读；
2. 读已提交（RC）：解决脏读，仍存在不可重复读、幻读；
3. 可重复读（RR 默认）：解决脏读、不可重复读，存在幻读；
4. 串行化：解决所有并发问题，性能最低，并发能力差。

### 3. 脏读、不可重复读、幻读 区别
- **脏读**：一个事务读取到其他事务**未提交**的临时数据；
- **不可重复读**：同一事务内，多次读取同一行数据，结果被其他事务修改而不一致；
- **幻读**：同一事务范围查询，前后查询行数不一致，被其他事务插入或删除数据。

### 4. InnoDB 怎么实现事务隔离？
基于 **MVCC 多版本并发控制**：通过 undo log 版本链 + read view 实现快照读；
RR 隔离级别通过间隙锁，一定程度上规避幻读问题。

### 5. MVCC 原理是什么？
每行数据包含隐藏字段：`DB_TRX_ID`（事务ID）、`DB_ROLL_PTR`（回滚指针）；
数据每次修改都会生成 undo log 历史版本，形成版本链；
快照读通过 read view 规则，从版本链中筛选出当前事务可见的数据版本，无锁读写，提升并发性能。

## 四、锁机制面试题

### 1. 锁分类
- 按粒度划分：表锁、行锁；
- 按类型划分：共享锁（S）、排他锁（X）；
- 行锁细分：记录锁、间隙锁、临键锁。

### 2. 表锁和行锁区别
- 表锁：锁定整张数据表，开销小、加锁快、并发性能低；
- 行锁：仅锁定单行数据，开销大、加锁慢、并发性能高，InnoDB 默认支持行锁。

### 3. 什么是意向锁？
分为意向共享锁（IS）、意向排他锁（IX），属于表级锁；
作用：快速判断表锁与行锁是否存在冲突，无需遍历所有行锁，提升锁冲突判断效率。

### 4. 记录锁、间隙锁、临键锁
- **记录锁**：锁定索引中已存在的某一行数据；
- **间隙锁**：锁定索引之间的空白间隙，阻止其他事务插入数据，缓解幻读；
- **临键锁**：记录锁 + 间隙锁的结合体，是 MySQL RR 级别默认的行锁算法。

### 5. 行锁什么时候会降级为表锁？
- SQL 未走索引或索引失效；
- 查询字段无任何索引，InnoDB 无法精准定位行数据，直接降级为表锁。

### 6. 死锁产生条件 & 如何避免
死锁四大必要条件：互斥条件、请求保持、不可剥夺、循环等待；
避免方案：
1. 统一多资源的访问顺序；
2. 拆分大事务，使用短事务、小事务；
3. 设置锁超时时间，开启数据库死锁检测；
4. 避免一次性为多个资源加锁。
