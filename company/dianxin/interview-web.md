# Web 与协议（口述问答）

> 对应 `readme.md` 中「Web & 协议」：Hertz / Gin、RESTful、WebSocket、gRPC / Protobuf。

## 1) Hertz 和 Gin 你更熟哪个？选型会看什么？

**口述参考：**  
Gin 生态成熟、上手快，适合常规 HTTP 服务。Hertz 偏 CloudWeGo 体系，和 Kitex 等组件协同好，性能与扩展点适合中台化服务。选型看团队标准、中间件生态、是否已有 RPC 网关一体化需求。

## 2) RESTful 设计里你最在意哪几条？

**口述参考：**  
资源名与动词分离、状态码语义一致、错误体结构统一、分页与版本策略清晰。对幂等写操作会显式用幂等键或业务唯一约束，避免重试导致重复副作用。

## 3) WebSocket 和长轮询怎么选？Agent 场景常见怎么做？

**口述参考：**  
强实时、服务端主动推送、连接数可控时用 WebSocket；仅需偶尔刷新用 SSE 或短轮询更简单。Agent 场景常见是 WS 推流式 token 或分片结果，配合心跳和鉴权刷新；网关层注意超时与连接迁移。

## 4) WebSocket 连接如何鉴权与续期？

**口述参考：**  
握手阶段用短期 JWT 或一次性 ticket 换会话；连接建立后按间隔续签或刷新 token。服务端维护会话与 userId 绑定，异常断开要清理状态。避免把长期密钥放在 query 上明文传输。

## 5) gRPC 相对 REST 的优势与代价？

**口述参考：**  
优势是强类型、二进制高效、流式一等公民；代价是浏览器侧和调试门槛、网关与版本治理要规划。对内服务链我更倾向 gRPC，对外仍常保留 REST 或 BFF。

## 6) Protobuf 版本与兼容性你怎么管？

**口述参考：**  
字段只增不改语义，用 optional / reserved 管理废弃字段；服务侧保持向后兼容读取。重大不兼容变更走新 package 或新 service，配合灰度发布与双写过渡期。

## 7) HTTP 网关层如何做超时、重试、熔断？

**口述参考：**  
超时按链路分层设置，客户端 < 网关 < 下游。重试只对幂等读或带幂等键的写，配合 jitter。熔断看错误率与慢调用比例，打开后快速失败并告警，避免雪崩。

## 8) 如何做流式响应（SSE / chunked）与背压？

**口述参考：**  

先说形态：**SSE** 适合浏览器单向流（文本事件、自动重连语义清晰），但要留意代理缓冲（Nginx 常要关 `proxy_buffering` 或配 `X-Accel-Buffering: no`）和连接超时。**Chunked HTTP** 更通用，二进制也能 chunked，网关兼容性有时更好。选型看客户端能力、是否必须走公司统一网关、以及是否需要「事件 ID + Last-Event-ID」这类 SSE 语义。

背压的核心是：**上游生产速度不能超过下游消费与 socket 可写的速度**，否则内存里会堆未发送数据。实现上常见做法是「读模型流 → 有界队列或带缓冲 channel → `http.ResponseWriter`/`Flusher` 写出」，队列长度就是可容忍的缓冲上限，满了就阻塞生产者或对上游暂停拉取（取决于你从模型拉还是从队列拉）。同时整条链路绑 **`context`**：用户断开、网关超时、业务取消任一触发，立刻停止向模型继续要 token，并关闭 writer，避免 goroutine 和 token 还在后台生成。

对 **Agent 逐 token** 场景，还要和 **上游模型超时、最大 token、RPM/TPM 配额** 对齐：网关超时要比「首 token + 流式间隔」更宽松，否则长思考会被误杀；又要在服务端设硬上限，防止慢流拖死连接池。可观测性上建议打点：**首包延迟、每 token 间隔、客户端断连率、chunk 写入阻塞时长**，出问题时能判断是模型慢、网络慢还是本机写阻塞。

最后补几条工程细节：**`Flush` 频率**别过高（syscall 与小包开销），可按批量或时间窗口 flush；错误不要在流中间塞非法 JSON，常见是先发完结构化结束帧再关连接；若中间要经过 **gRPC 双向流 → HTTP SSE** 的 BFF，要在转换层同样处理 cancel 与背压，避免 BFF 成为无界缓冲区。
