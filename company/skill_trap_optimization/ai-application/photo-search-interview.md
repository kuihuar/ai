这是一个**多模态 AI 教育应用**，用户对题目拍照后自动识别题目内容，匹配题库或由大模型生成解答。日均处理量级 [X 万题]，服务 [X 万] 用户。

## 三、技术架构与选型

### 3.1 架构

采用**微服务 + 管线式（Pipeline）**架构：

```
Gateway (Go/Gin)
  ├── 图片处理服务 (Go + gocv)
  ├── OCR 服务 (Python + PaddleOCR/Pix2Text)
  ├── 检索服务 (Go + pgvector/sqlx)
  ├── LLM 服务 (Python + OpenAI/Claude SDK)
  ├── 用户服务 (Go + PostgreSQL + Redis)
  └── 审核服务 (Go + 阿里云内容安全)
```

**为什么用混编（Go + Python）？**
- Go 做基础架构层：高并发网关、图片处理、向量检索、用户系统。优点是低延迟、编译部署简单。
- Python 做 AI 层：OCR、LLM 调用。原因是 CV/NLP 生态都在这边，直接用现成的 PaddleOCR、langchain 等库。

**Go 和 Python 之间如何通信？**
- 同步调用：gRPC（proto 定义清晰、性能高）
- 异步任务：消息队列（NSQ/Kafka），图片 OCR 为异步处理
- 大文件传输：OSS 预签名 URL 传递，不经过服务中转

### 3.2 关键选型及理由

| 组件 | 方案 | 当时为什么这么选 | 候选方案 | 为什么不选 |
|------|------|------------------|----------|------------|
| Web 框架 | Gin | 团队 Go 经验多，中文资料最丰富 | Chi, Fiber | Chi 生态不如 Gin；Fiber 不兼容 net/http |
| ORM | sqlx | 查询复杂（多表关联多），需要完全控制 SQL | GORM, Ent | GORM 复杂查询难控；Ent 学习成本高不适合项目周期 |
| 向量数据库 | pgvector | 团队已有 PostgreSQL 运维经验，向量量级不过百万 | Milvus, Qdrant | Milvus 需要单独运维，数据量级没到需要专用库的程度 |
| OCR | PaddleOCR | 中文效果最好，支持公式识别 | Tesseract | Tesseract 中文效果差太多 |
| LLM API | OpenAI + Claude | GPT-4 推理最强，Claude 代码/公式好 | 本地模型 | 解题对推理能力要求高，本地小模型不够 |
| 消息队列 | NSQ | Go 原生，运维简单，量级够用 | Kafka, RabbitMQ | Kafka 运维成本高；NSQ 部署一条命令，够用 |
| 缓存 | Redis | 通用，团队熟悉 | 本地缓存 | 多实例需要共享缓存 |
| 图片存储 | 阿里云 OSS | 公司已有阿里云设施 | MinIO (自建) | 运维成本 |

### 3.3 为什么用管线式（Pipeline）而不用端到端多模态大模型？

**面试官可能会追问这个问题**。

| 维度 | 管线式（OCR + 检索 + LLM） | 端到端（GPT-4V 直接解题） |
|------|---------------------------|--------------------------|
| 准确率 | **高**：题库检索到原题直接返回经过审核的答案 | 中：纯推理可能出错 |
| 延迟 | **低**：命中题库时 < 100ms | 高：每次 3-8 秒 |
| 成本 | **低**：命中题库时零 LLM 成本 | 高：每次调用多模态 API 要几毛到几块 |
| 题库复用 | **有** | 无 |
| 新题/偏题 | 依赖 LLM 兜底 | **强** |
| 可控性 | **高**：每一步可观测、可优化 | 低：端到端黑盒 |

**结论**：在题库覆盖率 > 70% 的场景下，管线式优势明显——大量请求命中题库无需调 LLM，成本低、延迟低且可解释。端到端多模态模型作为管线式的兜底方案——搜不到的偏题，降级调用 GPT-4V/Claude Vision。

## 四、核心难点与解决方案

### 难点 1：公式 OCR 准确率不够

**问题**：数学公式识别是拍照搜题的核心难点。传统 OCR（PaddleOCR 文字模式）对 `x² + √3 = 5` 这种内容容易把角标、根号、分式识别错。

**解决**：
- 引入 **Pix2Text** 的公式识别（MFR）模块，专门处理数学公式区域
- 版面分析阶段分离"纯文本区域"和"公式区域"，分别用不同模型处理
- 公式识别结果做后处理——LaTeX 语法检查 + 修复常见错误模式
- 最终效果：公式识别准确率从 80% 提升到 ~94%

### 难点 2：题库检索召回率不够

**问题**：同一道题换个说法、换个数、排版不同，Embedding 向量相似度就不高。

**解决**：
- **混合检索**：BM25（关键词） + Dense（语义），RRF 融合
- **题目指纹**：结构化特征（已知条件数、求解目标类型、关键数字）算 hash，精确匹配同一道题的不同变体
- **同题聚类**：用 Embedding 做聚类，人工确认后合并为"同一题目"
- **Rerank 精排**：初检 Top-100 → Cross-encoder Rerank → Top-5
- 最终效果：题库 Top-1 命中率从 55% 提升到 ~75%

### 难点 3：LLM 解答质量不稳定

**问题**：同样是数学题，有时候 LLM 跳步骤、给错答案、或有幻觉。

**解决**：
- **分科目 Prompt 精细化**：数学/物理/化学各有一套 Prompt，要求"逐步推导 + 验证"
- **Few-shot 示例**：每个科目选 3-5 个高质量解题示例放入 Prompt
- **Self-Consistency**：对低置信度题目跑 3 次取多数结果
- **自动验证**：将答案代入原题验证（如方程解代入是否成立）
- **反馈闭环**：用户 👎 的解答 → 人工审核 → 修正入库 → 下次命中题库
- 最终效果：解答好评率从 82% 提升到 ~92%

### 难点 4：高并发下的 OCR 排队

**问题**：高峰期（考试季、晚上）大量用户同时拍照，OCR 服务是 GPU 瓶颈，排队严重。

**解决**：
- OCR 服务作为异步任务，提交后返回 `task_id`，前端轮询结果
- GPU 集群弹性伸缩：基于 NSQ 队列深度自动扩缩 OCR 实例
- 优先队列：VIP 用户优先处理
- 客户端超时优化：图片预处理（裁剪、质量检测）在客户端完成，减少无效请求

## 六、面试常见追问准备

### Q1: 为什么不用端到端方案，像 GPT-4V 直接解题？

答：成本 + 题库价值。我们有 70%+ 的题目在题库中，管线式命中题库 < 100ms + 零 LLM 成本。端到端每次 3-8 秒 + 每次 0.5-2 元，得不偿失。但 GPT-4V 是我们的兜底方案——真正搜不到的偏题会降级给它。

### Q2: 题库从哪来？怎么保证答案质量？

答：初期人工录入 + 爬取公开题源 + 厂商合作。现在有用户反馈闭环——低分解答自动触发人工复核，纠正后入库，质量滚动提升。

### Q3: 并发量多大？怎么扛住的？

答：日常 QPS [X]，高峰期 [Y] 倍。OCR 异步化 + GPU 弹性伸缩 + 题库缓存命中。99% 的请求在 < 2s 内返回。

### Q4: 向量数据库为什么选 pgvector 而不是 Milvus？

答：量级决定。题库在百万级，pgvector 的 IVFFlat 索引延迟 < 10ms 够用。团队 PostgreSQL 运维成熟，不引入新组件。如果量级上亿会考虑 Milvus。

### Q5: 大模型成本怎么控制？

答：三层降本——(1) 题库命中免费，(2) 语义缓存 30% 命中率，(3) 模型分级（简单题用小模型）。目标是月成本的 70% 被前两层吃掉。

### Q6: 如果重新来一次，会做什么不同的选择？

答：(1) 题库先去重再做 Embedding，而不是先 Embedding 再去重；(2) OCR 模型直接上 Pix2Text 而不是先试 Tesseract 再换；(3) 更早建立 A/B 测试体系，能量化每次 Prompt 优化的效果。
