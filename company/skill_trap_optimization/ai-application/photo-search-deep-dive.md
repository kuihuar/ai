# 拍照搜题：检索召回率与 LLM 解答质量 深度剖析

## 第一部分：题库检索召回率

### 一、基础知识点

#### 1.1 信息检索的三代方法

| 代际 | 方法 | 代表 | 原理 | 核心局限 |
|------|------|------|------|----------|
| 第一代 | 关键词匹配 | TF-IDF, BM25 | 词频-逆文档频率统计匹配 | 同义词、换表述完全失效 |
| 第二代 | 语义检索 | Dense Embedding + 向量相似度 | 将文本映射到语义向量空间，计算余弦/欧氏距离 | 对精确词汇不敏感（人名、型号、公式） |
| 第三代 | 混合检索 | BM25 + Dense + Rerank | 结合两者优势，精排兜底 | 工程复杂度高 |

#### 1.2 BM25（Best Match 25）原理

BM25 是 TF-IDF 的概率升级版，核心公式：

$$BM25(q, d) = \sum_{t \in q} IDF(t) \cdot \frac{tf(t, d) \cdot (k_1 + 1)}{tf(t, d) + k_1 \cdot (1 - b + b \cdot \frac{|d|}{avgdl})}$$

关键参数：
- $k_1$（默认 1.5）：控制词频饱和速度，越大词频权重越大
- $b$（默认 0.75）：文档长度归一化程度，越大惩罚越长文档
- $IDF(t) = \log(\frac{N - n_t + 0.5}{n_t + 0.5})$：逆文档频率

**为什么 BM25 比 TF-IDF 好**：
- TF 项有饱和上限（词出现 100 次 ≠ 100 倍重要性），BM25 的 $k_1$ 参数控制了饱和曲线
- 考虑了文档长度归一化（长文档单靠词多不会天然占优）

**BM25 在拍照搜题中的局限**：
- "一个物体从 10 米高处落下"和"一物体于 10 米高处自由下落"——BM25 只匹配到"10米高"，漏了核心
- 公式是完全失灵的：$x^2 + 3x + 2 = 0$ 和 $x^2+3x+2=0$ 两个字符串 BM25 可能匹配不到（LaTeX 中的特殊字符被分词器切碎了）

#### 1.3 Dense Embedding（稠密向量检索）原理

**Bi-Encoder 结构**：
```
Query: "物体从高处落下的速度"  → Embedding Model → [0.12, -0.34, ..., 0.78]  (768维)
Doc:   "自由落体运动公式"       → Embedding Model → [0.15, -0.31, ..., 0.81]  (768维)

相似度 = cosine(query_vec, doc_vec) = (Q·D) / (|Q| × |D|)
```

**Embedding 模型的本质**：经过对比学习（Contrastive Learning）训练的句子表示模型，使得语义相近的文本在向量空间中距离近。

训练目标（InfoNCE Loss / Contrastive Loss）：

$$L = -\log\frac{\exp(sim(q, d^+) / \tau)}{\exp(sim(q, d^+) / \tau) + \sum_{d^-}\exp(sim(q, d^-) / \tau)}$$

- $d^+$：正样本（与 query 相关的文档）
- $d^-$：负样本（不相关的文档）
- $\tau$：温度系数，控制分布锐度

**Embedding 模型选型深入**：

| 模型 | 维度 | MTEB 中文得分 | 最大长度 | 优势场景 |
|------|------|--------------|----------|----------|
| BGE-M3 | 1024 | 领先 | 8192 | 通用中文，支持稠密+稀疏双模式 |
| BGE-large-zh | 1024 | 高 | 512 | 经典中文基准 |
| M3E-large | 1024 | 高 | 512 | 中文，社区活跃 |
| GTE-Qwen2-7B | 3584 | 最高 | 32K | 超长文本，效果最好但资源消耗大 |
| text-embedding-3-large | 3072 | 高（多语言） | 8191 | API 方案，零运维 |
| MathBERT | 768 | - | 512 | 数学公式专用 |

**拍照搜题场景的关键选择**：
- 数学题需要公式感知的 Embedding（MathBERT 或 BGE-M3 的稀疏模式）
- 超长题目（物理大题）需要支持长上下文的模型（GTE-Qwen2-7B）
- 如果走 API，text-embedding-3-large 支持 Matryoshka 表示学习，可以截断维度而不损失太多效果

#### 1.4 向量相似度度量

| 度量 | 公式 | 特点 | 适用 |
|------|------|------|------|
| 余弦相似度 | $\frac{A·B}{|A||B|}$ | 只关心方向，不关心大小 | L2 归一化后等价于内积 |
| 欧氏距离 | $\sqrt{\sum(A_i-B_i)^2}$ | 关心绝对距离 | L2 归一化后等价于余弦 |
| 内积 | $A·B$ | 计算最快 | 模型训练以点积为目标时最佳 |
| 曼哈顿距离 | $\sum |A_i-B_i|$ | 对异常值不敏感 | 较少用 |

**实践上**：绝大多数场景用余弦相似度。如果用 pgvector 的 `<=>` 运算符，它返回余弦距离（1 - 余弦相似度），注意要 `ORDER BY embedding <=> $1 LIMIT K`。

#### 1.5 近似最近邻（ANN）索引

向量检索在百万级以上需要 ANN 索引加速，不能暴力扫描。

| 索引类型 | 原理 | 精度 | 速度 | 内存 | 代表 |
|----------|------|------|------|------|------|
| **IVF**（倒排） | K-Means 聚类 → 只搜最近的 N 个簇 | 中(可调) | 快 | 中 | pgvector (IVFFlat) |
| **HNSW**（分层图） | 多层跳表图结构贪心搜索 | 高 | 最快 | 高 | pgvector, Milvus, Qdrant |
| **PQ**（乘积量化） | 高维向量压缩分解 | 略低 | 快 | 低 | Faiss |
| **DiskANN** | 磁盘上的图索引 | 高 | 快 | 极低 | 微软，超大规模 |

**pgvector 中的选择**：
```sql
-- IVFFlat: 需先建索引，速度快，内存适中
CREATE INDEX ON docs USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);

-- HNSW: 最新支持，精度最高，内存较大
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);
```

**实践建议**：
- 百万级以内：pgvector + HNSW 足够，不需要引入专用向量库
- 千万级以上：考虑 Milvus（分布式 HNSW）或 Qdrant
- 需要全文+向量混合：Elasticsearch 8.x+ 的 dense_vector + BM25 一起查

#### 1.6 Rerank（重排序）

**为什么需要 Rerank？**
Bi-Encoder（Embedding 模型）为了速度，把 query 和 doc 独立编码，交互只在最后的余弦计算。Cross-Encoder 让 query 和 doc 在模型内部做深度交叉注意力，精度远高于 Bi-Encoder，但速度慢（必须对每对 query-doc 重新推理）。

```
Bi-Encoder (Embedding):
  Query ──→ Model → vec_q ──┐
  Doc1  ──→ Model → vec_d1 ─┤→ cos(vec_q, vec_d1)
  Doc2  ──→ Model → vec_d2 ─┤→ cos(vec_q, vec_d2)
  ...                        │
  (文档可预先编码存储，查询时只编码 query 一次)

Cross-Encoder (Rerank):
  [Query, Doc1] → Model → Score1
  [Query, Doc2] → Model → Score2
  ...
  (每对都要重新过完整模型，但注意力是全交叉的)
```

因此最佳实践：**Bi-Encoder 粗筛 Top-N × Cross-Encoder 精排 Top-K**

```python
# 典型流程
candidates = bi_encoder.search(query, top_n=100)  # 快速粗筛 100 个
scores = cross_encoder.rerank(query, candidates)   # 逐对精排
top_k = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)[:5]
```

**Rerank 模型选型**：

| 模型 | 类型 | 中文 | 速度 | 说明 |
|------|------|------|------|------|
| Cohere Rerank v3 | API | 好(多语言) | 快 | 当前 SOTA，按搜索次数计费 |
| BGE-Reranker-v2-m3 | 开源 | 很好 | 中 | 中文最强开源方案 |
| BGE-Reranker-large | 开源 | 好 | 中 | 经典方案 |
| Jina Reranker v2 | API/开源 | 好(多语言) | 快 | 支持 8192 token 长度 |
| ColBERT | 延迟交互 | 中 | 中 | 介于 Bi 和 Cross 之间 |

### 二、实践改进全记录

#### 改进 1：从纯 Embedding 到混合检索

**原始状态**：
- 只用 text-embedding-3-small 做 Dense 检索
- 召回率 Recall@5 = 0.62

**问题诊断**：
- 大量题目的关键词（数字、专业术语、人名）在 Embedding 中权重被稀释
- 例如："求 $f(x) = x^3 - 6x^2 + 11x - 6$ 的零点"——Embedding 更关注语义"求函数零点"，而忽略"x^3 - 6x^2 + 11x - 6"这个核心特征

**改进方案**：
```
阶段一：Dense + Sparse 并行检索
  - BM25 做关键词通道：捕获数字、术语精确匹配
  - Embedding 做语义通道：捕获"求零点" = "解方程"的语义等价
  - RRF 融合：score = Σ 1/(60 + rank_i)

阶段二：加入 Cross-encoder Rerank
  - 粗排 Top 100 → BGE-Reranker 精排 → 取 Top 5
```

**改进后**：Recall@5 从 0.62 → 0.81

**RRF（Reciprocal Rank Fusion）实现**：

```go
func RRF(resultsList [][]ScoredDoc, k float64) []ScoredDoc {
    scores := make(map[string]float64)
    for _, results := range resultsList {
        for rank, doc := range results {
            scores[doc.ID] += 1.0 / (k + float64(rank+1))
        }
    }
    // 按融合分数降序排列
    sorted := rankByScore(scores)
    return sorted
}
```

#### 改进 2：题目指纹去重加速精确匹配

**问题**：大量"同一道题"因为排版、换行、标点差异被当成不同题，既浪费检索资源，又拉低命中率统计。

**改进方案**：
```
题目 → 结构化特征提取：
  1. 数字序列：[10, 9.8, 2]（提取所有数值）
  2. 关键实体：["自由落体", "高度"]
  3. 公式结构 hash：f(x)=x^2 → normalized LaTeX → SHA256
  4. 题型 + 学科 + 条件个数

五项组合 → MD5 → 题目指纹
```

```go
type QuestionFingerprint struct {
    Numbers     []float64  // 关键数值
    Entities    []string   // 命名实体
    FormulaHash string     // 归一化公式的 hash
    Subject     string     // 学科
    Type        string     // 题型
}

func (f *QuestionFingerprint) Hash() string {
    data := fmt.Sprintf("%v|%v|%s|%s|%s",
        f.Numbers, f.Entities, f.FormulaHash, f.Subject, f.Type)
    h := md5.Sum([]byte(data))
    return hex.EncodeToString(h[:])
}
```

**效果**：相同题目不同排版，指纹一致，精确匹配命中率从 12% → 35%。

#### 改进 3：Domain-Specific Embedding 微调

**问题**：通用 Embedding 模型在数学/物理题目上效果不够好。"向心力"和"圆周运动"语义很近但 embedding 距离不够近。

**改进方案**：
- 从题库中构建训练样本：同一道题的两个变体作为正样本对，不同题目作为负样本
- 用 Contrastive Learning 微调 BGE-M3
- 训练数据增强：同一题目做同义词替换、语序调换、数值修改

```
正样本对：
  ("物体从10米高处落下求落地速度", "一物体于10米高处自由下落求触地速率")
  ("求解方程 x²-5x+6=0", "x²-5x+6=0 的解是多少")

负样本对：
  ("物体从10米高处落下", "计算圆的面积公式")  ← 不同考点
```

**微调后效果**：领域内 Recall@5 从 0.81 → 0.88

#### 改进 4：Query 扩展（Query Expansion）

**问题**：用户拍照的题可能缺失关键信息（拍糊了、裁切不全），或口语化提问导致检索偏差。

**改进方案**：
```
原始 Query → LLM 改写为 3 个变体 → 多个变体同时检索 → 合并去重 → Rerank

原始: "这题怎么做"
改写1: "请解答以下数学题，涉及一元二次方程求解"
改写2: "求解 x²-5x+6=0 的步骤"
改写3: "因式分解法解 x²-5x+6=0"
```

**注意**：Query 扩展增加了检索延迟和 LLM 成本，只对低置信度（初始检索分数 < 阈值）的查询触发。

### 三、其他产品如何做检索

#### 3.1 作业帮 / 猿辅导（推测）

基于公开技术博客和招聘信息推测：

| 环节 | 推测方案 |
|------|----------|
| 题库规模 | 亿级别，经过多年累积 |
| 精确匹配 | 题目指纹 + 流水号，核心是题目归一化 |
| 语义检索 | 自研 Embedding 模型（基于学生搜索行为微调） |
| 索引 | 自研或定制的向量检索引擎（非开源方案） |
| Rerank | 结合点击率、采纳率、题目质量分的 Learning to Rank |
| 个性化 | 基于用户学段、教材版本的检索结果个性化重排 |

**核心壁垒**：
- **题目归一化能力**：同一道题的几百种不同问法归一到一个 ID 下
- **题库质量**：经过老师审核/修正的解答，比 LLM 生成的可信度更高
- **用户反馈信号**：亿级用户的点击/采纳/报错数据 → 持续优化排序

#### 3.2 Photomath（微软旗下）

- **不依赖题库检索**，而是用**符号计算引擎**直接解题
- 对算术、代数、微积分类题目，直接用计算机代数系统求解
- 对几何题，用几何定理推理引擎
- LLM 只用于解释步骤，不用于解题本身
- 优点：答案 100% 确定；缺点：无法处理文字题、证明题

**启示**：数学计算类题目，优先用计算引擎（符号计算/数值计算）而非 LLM。

#### 3.3 Google Lens / Socratic (Google)

- 图片 → 搜索不只是题目的文本，还有题目的**视觉特征**
- 对公式的识别用专门的 Math OCR 模型
- 搜索引擎级别的索引和排序能力
- 结合 Knowledge Graph 提供知识点关联

#### 3.4 Wolfram Alpha

- 完全用符号计算 + 知识库，不用 LLM
- 知识库覆盖数学、物理、化学等学科的结构化数据
- 输入是**结构化的计算查询**而非自然语言题目
- 与拍照搜题互补：拍照 → OCR → 结构化查询 → Wolfram 计算 → 返回

#### 3.5 对比总结

| 产品 | 核心检索策略 | 解答生成方式 | 核心壁垒 |
|------|-------------|-------------|----------|
| 作业帮/猿辅导 | 题库检索为主（亿级题库） | 题库答案 + 教师审核 | 题库量+质量+用户数据 |
| Photomath | 无题库，符号计算引擎 | 计算引擎自动求解 | 符号计算+几何推理引擎 |
| Google Socratic | 搜索引擎级别检索 | 题库+LLM | 搜索基础设施+Knowledge Graph |
| Wolfram Alpha | 结构化计算查询 | 符号计算+知识库 | 30年积累的领域知识库 |
| **我们的方案** | 多级检索（指纹→BM25→语义→LLM） | 题库+LLM混合 | 管线式成本控制+数据闭环 |

## 第二部分：LLM 解答质量不稳定

### 一、LLM 生成质量的基础知识

#### 1.1 LLM 为什么会产生低质量答案

**核心原因：概率生成的本质**

LLM 本质是预测 $P(token_t | token_{<t}, context)$，每一步都选"最可能的下一个 token"，但最可能 ≠ 最正确。在长链推理中，错误会级联放大：

```
第 1 步：正确率 95%
第 2 步：正确率 95% × 95% = 90%
第 5 步：正确率 95%^5 = 77%
第 10 步：正确率 95%^10 = 60%
```

数学题通常 5-10 步推导，错误率自然就高了。

**其他原因**：

| 原因 | 说明 |
|------|------|
| 训练数据噪声 | 模型见过错误的解题步骤 |
| 最大似然局限 | 训练目标是最小化困惑度，不是最大化正确率 |
| 缺乏真正的推理 | 模型是模式匹配，不是逻辑推导 |
| 数值计算不准 | 大模型没有内置精确计算器，依赖记忆中的数字 |
| 上下文混淆 | 检索到的相似题"带偏"了解答方向 |
| 公式理解偏差 | LaTeX 公式在训练语料中可能是噪音 |

#### 1.2 Temperature 与 Top-P 采样原理

这两个参数控制 LLM 生成的随机性和确定性：

**Temperature**：
$$P_i = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$$

- $T = 0$：贪婪解码，永远选概率最高的 token（最确定，但缺乏多样性）
- $T = 1$：原始概率分布
- $T > 1$：拉平分布，低概率 token 被放大（更随机、更有"创意"，但可能胡说）

**Top-P（Nucleus Sampling）**：
- 按概率从高到低累积，只保留累积概率 ≤ P 的 token
- $P = 0.1$：只保留概率最高且累积 ≤ 10% 的极少数 token（极保守）
- $P = 0.9$：保留较多 token，平衡确定性和多样性

**解题场景推荐**：
- 计算/推导：Temperature=0, Top-P=0.1（最确定）
- 解释步骤：Temperature=0.3, Top-P=0.7（稍灵活，避免机械重复）
- 作文/创意：Temperature=0.8, Top-P=0.9

#### 1.3 Self-Consistency 原理（MIT, 2022）

一篇重要的论文 [Self-Consistency Improves Chain of Thought Reasoning in Language Models](https://arxiv.org/abs/2203.11171) 的核心思想：

**同一个问题跑 N 次（用不同采样路径），取出现最多的答案。**

为什么有效：
- 推理路径有随机性（sampling），正确答案有多个推理路径都能到达
- 错误答案的推理路径往往是随机且各不相同的
- "多数投票"能过滤掉这些随机错误

```python
def self_consistency(question, n_samples=5):
    answers = []
    for _ in range(n_samples):
        # 使用 Temperature > 0，每次采样不同
        answer = llm.generate(question, temperature=0.7)
        answers.append(extract_final_answer(answer))
    # 多数投票
    return Counter(answers).most_common(1)[0][0]
```

**代价**：成本 × N 倍。实际中只对"高难度/低置信度"的题使用。

#### 1.4 幻觉（Hallucination）的类型与机制

| 类型 | 表现 | 例子 |
|------|------|------|
| **事实性幻觉** | 编造不存在的事实 | "牛顿第三定律是 F=mv" |
| **忠实性幻觉** | 偏离题目要求 | 题目要求求解，变成证明 |
| **逻辑跳跃** | 省略关键推导步骤 | 从 a=b 直接跳到结论 |
| **数值错误** | 计算过程正确但结果算错 | 3x=9 → x=6 |
| **公式幻觉** | 使用错误的公式 | 混淆相似公式 |

**检测方法**：

| 方法 | 做法 | 效果 |
|------|------|------|
| 答案代入验证 | 把 LLM 的解代入原题检查 | 数学题有效，文字题无效 |
| LLM 自检 | 让 LLM 检查自己的解答 | 中等（自己查自己不可靠） |
| 双模型交叉验证 | 两个不同模型比对结果 | 高（成本也高） |
| 结构化输出验证 | 约束输出格式，检查完整性 | 格式错误有效，内容错误无效 |
| 不确定性量化 | 输出 token 的概率熵 | 可做质量预警，需深入实现 |

### 二、实践改进全记录

#### 改进 1：分科目精细化 Prompt

**原始 Prompt**（所有科目共用）：
```
请解答以下题目，给出详细步骤。
```

**改进后**（分科目 + 角色 + 约束）：
```markdown
# 数学题 Prompt
你是资深高中数学教师。请按以下要求解答：

1. **审题**：明确已知条件和求解目标
2. **分析**：判断考点，选择解题方法（代数法/几何法/数形结合）
3. **推导**：每一步写出依据（定理/公式），用 LaTeX 格式
   - 第一步：...
   - 第二步：...
4. **答案**：明确写出最终结果
5. **验证**：将答案代入原题检验

{检索到的相似题和解答，仅供参考}

题目：{用户题目}
```

**效果**：分科目 Prompt 后，解答好评率从 82% → 87%。

**为什么有效**：
- "角色设定"激活了模型中教师风格的教学内容
- "逐步列出依据"强制 LLM 不能跳步
- "代入验证"提供了自检环节

#### 改进 2：模型分级路由

**原始方案**：所有题都用 GPT-4

**改进方案**：

```
题目 → 学科分类 + 难度评估
          ↓
    简单题（四则运算、单词翻译）
          → GPT-4o-mini / Claude Haiku（成本 1/20）
          ↓
    中等题（方程组、阅读理解）
          → GPT-4o（平衡成本和效果）
          ↓
    难题（竞赛题、复杂证明）
          → GPT-4 / Claude Opus（最强推理）
          ↓
    数学计算题（可精确计算的）
          → 符号计算引擎（而非 LLM）
```

**难度评估规则**：
- 题目长度 > 200 字 → 可能性大（信息量大）
- 包含"证明"/"是否成立"/"讨论" → 可能较难
- 涉及竞赛知识 → 高水平

**效果**：LLM 成本降低 40%，整体好评率反而微升（因为难题给了更强的模型）。

#### 改进 3：公式答案自动验证（符号计算）

**核心思路**：能用计算引擎验证的，不用人。

```
LLM 生成解答 → 提取"最终答案表达式"
                    ↓
              ├── 方程类：代入原方程验证
              │    例：LLM说 x=2 是方程 x²-3x+2=0 的解
              │    验证：2² - 3×2 + 2 = 4-6+2 = 0 ✓
              │
              ├── 计算类：用 Python 符号计算（SymPy）独立求解
              │    LLM 答案 vs SymPy 答案 → 一致则通过
              │
              ├── 几何类：无法自动验证 → 标记为需人工复核
              │
              └── 验证失败 → 重新生成或降级给用户标记
```

```python
# 符号计算自动验证
import sympy as sp

def verify_equation_solution(equation_str, claimed_solution):
    """验证 LLM 给的一元方程解是否正确"""
    x = sp.Symbol('x')
    try:
        eq = sp.sympify(equation_str.replace("=", "-(") + ")")
        result = eq.subs(x, claimed_solution)
        return abs(float(result)) < 1e-9
    except:
        return None  # 无法解析，需人工
```

**效果**：方程类题目的验证准确率达到 99%+，自动拦截了约 5% 的错误解答。

#### 改进 4：多路生成 + 投票

```
同一道题 → 3 条生成路线：

路线 1：GPT-4 + CoT Prompt（步骤推导）
路线 2：Claude + CoT Prompt（步骤推导）
路线 3：GPT-4 + 不同的 Few-shot 示例

最终答案比对：
  - 3 条路线答案一致 → 高置信度，直接返回
  - 2 条一致，1 条不同 → 返回多数，加"答案仅供参考"提示
  - 3 条都不同 → 转人工复核，返回"暂无答案"
```

**为什么有效**：不同的模型的错误分布不同，同时出错的概率极低。

**缺点**：成本 × 3。只对 **高价值题目**（用户多次搜索且无题库答案）触发。

#### 改进 5：反馈闭环与 RLHF 式优化

```
用户反馈（👍/👎 / 报错原因）
          ↓
    ┌── 低分解答自动入审核队列
    │
    ├── 人工审核团队（或高级 LLM + 人工抽检）
    │        ↓
    │   修正答案 → 写入题库 → 下次命中题库直接返回审核过的答案
    │
    ├── 报错原因分类统计
    │        ↓
    │   Top 原因 → 优化 Prompt / 升级模型 / 关闭该题型的 LLM 生成
    │
    └── 高质量 👍 解答 → 纳入 Few-Shot 示例库
```

**效果**：运行 3 个月后，题库扩充 30%，需 LLM 生成的题目比例下降 12 个百分点。

#### 改进 6：置信度分级展示

不是所有解答都同等可信。对用户诚实比假装完美更有利。

```
置信度评估规则：
  - 高（≥ 0.85）：题库命中 + 人工审核 → "官方解答"
  - 中（0.7-0.85）：题库命中 + 多人 👍→ "精选解答"
  - 低（0.5-0.7）：LLM 单次生成 + 无验证 → "AI 解答，仅供参考"
  - 不确定（< 0.5）：多路生成结果不一致 → "暂未找到可靠答案，试试手动输入"
```

### 三、其他产品如何保证解答质量

#### 3.1 作业帮 / 猿辅导：题库为王 + 人工审核

- **不依赖 LLM 直接给用户答案**。LLM 用于辅助生成草稿，最终展示的是题库中经过审核的答案
- 答疑老师团队（数万人）：审核、修正、补充解析
- 质量保障流程：题目录入 → 机器初解 → 教师审核 → 质量抽检 → 发布
- 用户报错机制：报错的题目优先级最高，24h 内修正

**启示**：要真正高质量，题库 + 人工审核是绕不开的壁垒。LLM 可以加速，但不能完全替代。

#### 3.2 Photomath：符号计算引擎，答案 100% 确定

- 对计算类题目，完全不用统计方法，而是用确定性的符号计算
- 自研了几何定理推理引擎
- LLM 只做"步骤解释"（把计算引擎的中间结果翻译成人话）
- **答案生成和步骤解释解耦**：计算引擎负责"对不对"，LLM 负责"好不好读"

**启示**：计算题和推理题应该分开处理。计算用引擎，推理用 LLM。

#### 3.3 ChatGPT / Claude：RLHF + 红队测试

- RLHF（人类反馈强化学习）：训练一个奖励模型，再微调 LLM
- Constitutional AI（Claude）：定义 AI 的行为准则，自监督对齐
- 红队测试（Red Teaming）：专门的人试图让模型出错，收集案例改进
- 拒绝回答机制：不确定时直接说"我不确定"，优于给出错误答案

**启示**：不要害怕说"不知道"。确保 LLM 在不确定时拒绝回答，比硬要给个可能错误的答案好得多。

#### 3.4 Wolfram Alpha：确定性计算 + 知识库

- 答案不是"生成"的，而是从知识库和科学数据库中"计算/查找"的
- 所有数据由领域专家结构化整理
- 涉及计算的全部用符号计算引擎
- **LLM + Wolfram 混合**：LLM 负责理解题目，Wolfram 负责精确计算

**启示**：LLM 最强的能力是理解题目、拆解问题，不是精确计算。应该让 LLM 做计划，让计算引擎做执行。

#### 3.5 Khan Academy (Khanmigo)：AI 辅导而非 AI 解答

- **不直接给答案**，而是像人类家教一样引导
- "你觉得从哪里开始？"
- "你试过因式分解吗？"
- 通过苏格拉底式提问引导学生自己解决
- 解答的"质量"体现为引导的质量，而不是最终答案的正确率

**启示**：改变产品定位——从"拍照给答案"变为"拍照辅导学习"。辅导式交互的容错性远高于直接给答案。

#### 3.6 对比总结

| 产品 | 质量保障核心策略 | 适用场景 |
|------|-----------------|----------|
| 作业帮/猿辅导 | 亿级题库 + 人工审核 | 全学科，K12 |
| Photomath | 符号计算引擎 | 数学计算题 |
| Wolfram Alpha | 知识库 + 符号计算 | 数理化精确计算 |
| ChatGPT/Claude | RLHF / Constitutional AI | 通用问答 |
| Khanmigo | 辅导式交互（不给答案） | 教育场景 |
| **我们的方向** | 管线式（计算引擎 + 题库 + LLM + 人工） | 综合性拍照搜题 |

## 四、两个问题的交汇：检索质量 如何影响 解答质量

这是容易被忽视的，但其实是核心问题。

**Garbage In, Garbage Out**：如果检索到的"相似题"根本不对，LLM 会被带偏。

```markdown
❌ 检索错了：
  用户题目：求函数 f(x)=x²+2x+1 的最小值（二次函数最小值）
  检索到：求 x²+2x+1=0 的解（一元二次方程）
  LLM 被误导 → 给出了错误的"解方程"答案

✅ 检索对了：
  用户题目：求函数 f(x)=x²+2x+1 的最小值
  检索到：用配方法求二次函数最小值（相似题型）
  LLM 参考正确示例 → 给出正确解答
```

**因此，检索质量是解答质量的第一道防线。** 如果检索质量不行，Prompt 再精细、模型再强大，生成质量也会天然受限。

**解决思路**：
1. 检索分数 < 阈值的题目，**不要把检索结果注入 Prompt**，直接让 LLM 独立解答
2. 在 Prompt 中强调"如果参考题目与你的题目不同，忽略参考，独立作答"
3. Rerank 阶段加入**题目类型一致性检查**：检索到的题目和用户题目必须是同一题型，否则过滤
