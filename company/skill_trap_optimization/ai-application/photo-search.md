# 拍照搜题：AI 应用落地技术全链路拆解

## 一、概述

拍照搜题是典型的多模态 AI 应用，融合了计算机视觉（CV）、自然语言处理（NLP）、信息检索、大语言模型等多个 AI 子领域。

**核心流程**：

```
用户拍照 → 图像预处理 → OCR/公式识别 → 题目文本
                                              ↓
                              ┌─ 题库精确匹配 → 直接返回答案
                              │
                              └─ 无精确匹配 → 向量检索(RAG) → LLM生成解答
```

## 二、技术全链路拆解

### 2.1 图像预处理

| 步骤 | 技术 | 作用 |
|------|------|------|
| 去模糊/去噪 | OpenCV 高斯滤波、双边滤波 | 提升 OCR 识别率 |
| 倾斜校正 | 霍夫变换/Hough Transform 检测直线，透视变换矫正 | 侧拍的矫正 |
| 光照均衡 | CLAHE（自适应直方图均衡化） | 解决阴影/曝光不均 |
| 区域检测 | 目标检测（YOLO/Faster R-CNN）定位题目区域 | 裁剪无关内容 |
| 版面分析 | LayoutLM / PaddleOCR layout | 区分题目/图表/公式区域 |

```go
// Go 中图像预处理（使用 gocv）
import "gocv.io/x/gocv"

func preprocess(img gocv.Mat) gocv.Mat {
    // 灰度化
    gray := gocv.NewMat()
    gocv.CvtColor(img, &gray, gocv.ColorBGRToGray)

    // 高斯去噪
    gocv.GaussianBlur(gray, &gray, image.Pt(5, 5), 0, 0, gocv.BorderDefault)

    // 自适应阈值二值化
    binary := gocv.NewMat()
    gocv.AdaptiveThreshold(gray, &binary, 255,
        gocv.AdaptiveThresholdGaussian, gocv.ThresholdBinary, 11, 2)

    return binary
}
```

### 2.2 OCR（光学字符识别）

| 方案 | 优势 | 劣势 | 适用 |
|------|------|------|------|
| **PaddleOCR** | 中文最强，支持公式识别 | Python 生态，需服务化 | 中文题目 |
| **Tesseract** | 开源，多语言 | 中文效果一般 | 英文/数字 |
| **MathPix API** | 公式识别极好 | 收费，有调用限制 | 数学公式转 LaTeX |
| **Pix2Text** | 中文+公式混合识别 | 需 GPU | 混合型题目 |
| **Florence-2 / Qwen-VL** | 多模态大模型直接读图 | 延迟较高 | 复杂 layout 题目 |

**公式识别（LaTeX）**：数学题的核心难点。传统 OCR 对 `x²+3x+2=0 → $x^2 + 3x + 2 = 0$` 这种 LaTeX 转换不敏感，需要专门的公式识别模型（MathPix、Pix2Text 的 MFR 模块）。

### 2.3 文本理解与后处理

OCR 输出的原始文本通常含噪音，需要：

```
OCR 输出 → 文本纠错 → 公式格式化（LaTeX） → 题目结构化
```

| 步骤 | 技术 |
|------|------|
| 文本纠错 | 基于 BERT 的纠错模型（pycorrector）+ 领域词典 |
| 公式格式化 | LaTeX parser，修复 OCR 引入的语法错误 |
| 题目结构化 | 正则/NER 提取已知条件、求解目标 |
| 题目分类 | 文本分类模型 → 数学/物理/化学/英语 |

## 三、检索策略

### 3.1 多级检索架构

```
题目文本
    ↓
第一级：精确匹配（Hash）
    → 题目 hash 值查题库 → 命中 → 直接返回缓存答案
    ↓ Miss
第二级：关键词检索（BM25）
    → 关键词匹配 → 同题不同表述 → 排名前 3
    ↓ 分数不够
第三级：语义检索（向量相似度）
    → Embedding 检索 → 相似题目 Top-K
    ↓
Rerank（Cross-encoder）
    → 取 Top-3
    ↓ 相似度 < 阈值
第四级：LLM 直接生成
    → 无相似题目，GPT-4 直接解题
```

### 3.2 题库构建

```
原始题目（文本 + LaTeX + 答案 + 解析）
        ↓
  题目 Embedding（向量化）
        ↓
  存入向量数据库 + 倒排索引
        ↓
  支持：精确匹配 / 关键词搜索 / 语义搜索
```

**题库 Embedding 方案**：
- 普通题目：text-embedding-3-small / BGE
- 数学题：需要公式感知的 Embedding（MathBERT 或直接存 LaTeX 字符串）

### 3.3 相似度计算

```go
// 混合检索融合
func hybridSearch(query string, topK int) []Doc {
    // 1. BM25 关键词检索
    sparseResults := bm25Search(query, topK)

    // 2. Dense 语义检索
    queryVec := embedder.Embed(query)
    denseResults := vectorDB.Search(queryVec, topK)

    // 3. RRF 融合
    merged := rrf(sparseResults, denseResults)

    // 4. Rerank
    return reRank(query, merged, 5)
}
```

## 四、解答生成

### 4.1 Prompt 设计

```
你是专业的{科目}老师。请根据以下题目和参考解答，给出详细的解题步骤。

题目类型：{题目类型}
难度：{难度}

题目：{题目文本}

参考相似题及解答：
{检索到的相似题+答案}

要求：
1. 逐步推导，每一步说明依据
2. 涉及公式时用 LaTeX 格式
3. 最后给出检查答案的方法
```

### 4.2 分科目处理

| 科目 | 特殊处理 |
|------|----------|
| **数学** | 公式识别（MathPix/Pix2Text），LaTeX 渲染展示 |
| **物理** | 公式 + 单位换算 + 受力分析图 |
| **化学** | 化学方程式配平、结构式识别 |
| **英语** | 语法分析、翻译（可用 GPT 直接处理） |
| **语文** | 文言文翻译、阅读理解（RAG + LLM） |

### 4.3 多模态模型方案（简化版）

最新的视觉大模型可以直接端到端处理，跳过传统 OCR 步骤：

```
拍照图片 → Florence-2 / GPT-4V / Qwen-VL → 直接输出解答
```

**优缺点**：

| 方式 | 管线式（OCR + 检索 + LLM） | 端到端多模态 |
|------|---------------------------|-------------|
| 精确度 | 高（检索到原题直接给答案） | 中（纯推理可能错） |
| 题库价值 | 可积累题库、优化检索 | 无题库复用 |
| 成本 | 低（大部分命中缓存/题库） | 高（每次都调大模型） |
| 新题/偏题 | 依赖 LLM 最终兜底 | 好（多模态推理强） |
| 延迟 | 命中题库时 < 100ms | 2-5s |

**最佳实践**：管线式为主（题库命中率高）+ 多模态兜底（真的搜不到的图直接用 4V 解）。

## 五、系统架构设计

### 5.1 整体架构

```
┌──────────┐
│ 客户端    │ 拍照 → HTTP Upload
└────┬─────┘
     ↓
┌─────────────────────────────────────┐
│             API Gateway              │  鉴权、限流、图片格式校验
└────┬────────────────────────────────┘
     ↓
┌─────────────────────────────────────┐
│          图片处理服务（Go）           │  压缩、格式转换、预处理
└────┬────────────────────────────────┘
     ↓
┌─────────────────────────────────────┐
│          OCR 服务（Python）           │  PaddleOCR / Pix2Text
└────┬────────────────────────────────┘
     ↓
┌─────────────────────────────────────┐
│          检索服务（Go）              │  精确匹配 → BM25 → 向量检索 → Rerank
└────┬────────────────────────────────┘
     ↓
┌──────────┐
│ 命中题库？ │
└──┬───┬───┘
  Yes  No
   ↓    ↓
直接  ┌─────────────────────┐
返回  │  LLM 服务（Python）   │  GPT-4 / Claude / 本地模型
      └────────┬────────────┘
               ↓
      ┌─────────────────────┐
      │  解答入库 + 返回     │
      └─────────────────────┘
```

### 5.2 服务职责

| 服务 | 语言 | 职责 |
|------|------|------|
| API Gateway | Go | 鉴权、限流、图片校验、文件上传 OSS |
| 图片处理 | Go (gocv) 或 Python | 压缩、去噪、方向矫正、区域裁剪 |
| OCR | Python | PaddleOCR / Pix2Text，支持公式 |
| 检索服务 | Go | 题库匹配 + 向量检索 + Rerank |
| LLM 服务 | Python | 调用 GPT-4/Claude，统一 prompt、重试、降级 |
| 题库管理 | Go | 题目 CRUD、embedding 更新、索引维护 |

### 5.3 关键性能优化

| 优化点 | 方案 |
|--------|------|
| 图片体积 | 客户端压缩到 < 500KB再上传（JPG quality 85） |
| OCR 延迟 | GPU 部署 PaddleOCR，单图 < 500ms |
| 检索延迟 | 题库 1000 万内用 pgvector + IVFFlat 索引，< 10ms |
| LLM 延迟 | 流式返回，首 token < 1s |
| 题库命中率 | 同题不同问法去重 → Embedding 聚类 → 提高命中 |
| 缓存 | 完全相同图片 hash 缓存（用户重复上传的同一张图） |

### 5.4 数据闭环

```
用户拍照 → OCR → 检索 → LLM解答 → 返回
                                  ↓
                            用户反馈（👍/👎 / 报错）
                                  ↓
                            低评价解答 → 人工审核 → 修正入库
                                                  ↓
                                            下次检索命中
```

## 六、知识点拆解总结

拍照搜题这条链路覆盖了以下 AI 知识点，按应聘岗位侧重点不同：

| 岗位侧重 | 核心知识 |
|----------|----------|
| **后端工程师（Go）** | API Gateway、图片处理、向量检索服务、缓存策略、服务编排、高并发 |
| **算法工程师（CV）** | 图像预处理、版面分析、OCR、公式识别 |
| **算法工程师（NLP）** | RAG 检索、Embedding、Rerank、LLM prompt |
| **MLOps / 工程** | GPU 推理部署、模型服务化、流水线编排、监控 |
| **产品** | 题库设计、反馈闭环、分科目策略、成本评估 |

**面试时如何回答"你能设计一个拍照搜题系统吗"**：
1. 先画出全局流程图（拍照 → OCR → 检索 → 解答）
2. 讲出多级检索的降级链路（精确 → 语义 → LLM）
3. 说明选型的取舍（管线式 vs 端到端多模态）
4. 展示对成本/延迟/准确率的权衡意识
