# 01. Go + Python 项目架构口述题

## 1) 为什么使用 Go + Python 混合架构？

**口述主答（60~90 秒）：**  
我们的业务是“高并发在线请求 + 模型能力快速迭代”双重诉求。Go 负责 API 网关和核心编排，因为并发性能、内存控制和稳定性更好；Python 负责模型推理和数据处理，因为算法生态和迭代效率更高。架构上我们通过 gRPC/protobuf 做强契约隔离：业务层只依赖能力接口，不感知模型实现细节。这样可以把稳定性和迭代速度分别做到最优。代价是跨语言调用复杂度上升，所以我们配了统一错误码、版本兼容窗口和契约测试，降低协作成本。

**高频追问：**
- 为什么不单语言统一？
- 跨语言调用延迟怎么控制？
- 出故障如何快速判断在 Go 端还是 Python 端？

**回答要点：**
- 讲清“分工不是技术偏好，而是业务目标驱动”。
- 明确“统一契约 + 统一观测 + 统一发布流程”。

---

## 2) 你的架构分层怎么设计？

**口述主答（60~120 秒）：**  
我一般按四层设计：接入层、编排层、能力层、数据层。接入层做鉴权、限流、参数校验；编排层承接业务状态机和流程路由；能力层沉淀模型推理、检索、规则引擎；数据层由 MySQL、Redis、ES 分别承担权威存储、热点缓存、检索分析。分层关键是“单向依赖，跨层只走接口”，避免服务互相穿透导致维护失控。接口层所有请求都带 trace_id、tenant_id、request_version，保证可追踪、可灰度、可回滚。

**高频追问：**
- 哪层最容易演进？
- 哪层最不允许变更？
- 如何避免编排层变成巨石服务？

**回答要点：**
- 用“业务变化频率”解释层级稳定性。
- 提到“领域拆分 + 编排去状态化 + 旁路能力下沉”。

## 3) Go 与 Python 接口如何保证长期可维护？

**口述主答（60~90 秒）：**  
我会把接口治理当成“产品化能力”。第一，统一 protobuf 契约，字段只做向后兼容新增，不做破坏性删除。第二，协议里固定元信息字段（trace_id、deadline、caller、model_version）。第三，建立契约测试：每次 Go 或 Python 变更都自动跑兼容验证。第四，接口版本采用双窗口策略，新旧版本并行一段时间，灰度完成后再下线旧版本。这样能避免“我改了字段你没跟上”的跨团队事故。

**高频追问：**
- 字段语义变化怎么处理？
- 旧版本拖太久怎么办？
- 错误码如何避免冲突？

## 4) 混合服务怎么发布与回滚？

**口述主答（60~90 秒）：**  
发布策略是“先能力后编排，先小流量后全量”。通常先升级 Python 能力服务并保持协议兼容，再灰度 Go 编排启用新能力。灰度期间实时看错误率、超时率、业务转化指标。回滚优先走开关和路由回切，其次才是版本回滚，保证止损速度。上线前强制经过单测、契约测试、压测基线和灰度验收，避免把风险留到生产。

**高频追问：**
- 为什么先回切流量而不是马上回滚代码？
- 线上发现版本不兼容怎么止血？
- 如何定义灰度扩容阈值？

---

## 5) 面试官追问“你在这个项目里最关键的贡献是什么”怎么答？

**口述主答（60 秒）：**  
我最关键的贡献是把“跨语言协作风险”前置治理：通过统一契约、统一可观测、统一灰度流程，把故障定位时间从小时级降到分钟级，发布成功率显著提升。这个贡献不只是写了某个功能，而是提升了团队交付确定性，这对复杂 Agent 业务是长期价值。

**建议补充量化指标：**
- 平均排障时长从 X 分钟降到 Y 分钟。
- 发布失败率从 A% 降到 B%。
- P95 延迟从 Mms 降到 Nms。
