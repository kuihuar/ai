# ES 集群、分片与副本

---

## 1. 主分片（primary）和副本（replica）的区别？

**知识点：**
- Primary：索引创建时数量固定（7.x+ 默认 1，可调），负责写入路径。
- Replica：primary 的拷贝，提供读扩展 + 高可用；数量可动态 `PUT settings`。
- 同一分片的 primary 和 replica 不会落在同一节点。

**口述：**
> 主分片决定数据如何切分和写入路由，副本是主分片的镜像。写一定落到 primary，读可以打到 primary 或 replica 做负载。副本数可以在线调，但主分片数索引创建后不能改，要改只能 reindex 到新索引。设计时我会让总分片数（primary×(1+replica)）和节点数成合理倍数，避免单机扛太多分片。

---

## 2. 主分片数量怎么定？定多了/少了会怎样？

**知识点：**
- 过少：单分片过大 → 恢复慢、迁移慢、热点集中。
- 过多：每个分片有 Lucene 开销（内存、文件句柄）→ 小集群扛不住。
- 经验：单分片目标几十 GB 量级（日志可更大，需压测）；分片数 ≈ 未来数据量 / 单分片目标。
- 公式：节点能稳定承载的分片数，官方曾建议每节点 < 20~50 shards（视 heap 而定）。

**口述：**
> 主分片数本质是并行度和容量的折中。太少会导致单个分片几十上百 GB，节点故障恢复要很久；太多则分片元数据和 merge 开销把 heap 吃光。我一般会按预估数据总量和保留周期算索引大小，再除以目标单分片大小得到 primary 数，并结合节点数和副本算总分片，最后用压测验证 P99 和恢复时间。

## 3. routing 是什么？自定义 routing 的场景？

**知识点：**
- 默认 routing = `_id`；相同 routing 必落同一 primary shard。
- 自定义 routing：如 `user_id`，同一用户文档同分片，便于按用户删/查。
- 风险：routing 分布不均 → 分片热点（skew）。

**口述：**
> routing 决定文档去哪个分片。如果业务按租户查询很多，可以把 tenant_id 当 routing，让同一租户数据局部性更好。但要注意租户大小差异，大租户会把某个分片打热，这时要拆分索引或二级路由策略，不能盲目自定义。

## 4. 集群节点角色有哪些？

**知识点：**
| 角色 | 作用 |
|------|------|
| master-eligible | 集群元数据、分片分配决策 |
| data (hot/warm/cold/frozen) | 存数据、执行查询 |
| ingest | 预处理 pipeline |
| coordinating only | 只转发，不存数据（大查询聚合节点） |
| machine learning | ML 作业 |

**口述：**
> 生产里会把 master 和数据节点分离：master 节点轻量、奇数个，专管集群状态；data 节点按 hot/warm/cold 分层扛读写；有大 ingest 或 enrich 需求再加 ingest 节点。协调节点单独拆出来，适合聚合很重、不想和数据节点抢 heap 的场景。

## 5. 脑裂（split-brain）是什么？怎么防？

**知识点：**
- 原因：网络分区，多个节点各自认为自己是 master，元数据不一致。
- 7.x+：**cluster bootstrapping** + **voting configuration**，需 quorum 才能选主。
- 历史手段：`discovery.zen.minimum_master_nodes`（已演进）。
- 实践：专用 master 节点（`node.roles: [ master ]`）、奇数 master 节点、避免 master 节点跑重查询。

**口述：**
> 脑裂就是集群里同时出现两套 master 视图，分片分配会乱。现代 ES 用投票配置保证只有多数派能选主，所以 master 节点要奇数，并且和网络隔离、负载均衡健康检查配合。另外 master 节点不要当 data 节点狂跑查询，否则 GC 停顿会导致误判断主。

## 6. cluster health：green / yellow / red 含义？

**知识点：**
- **green**：所有 primary 和 replica 都已分配且 active。
- **yellow**：所有 primary 在，但有 replica 未分配（常见：单节点集群、磁盘紧、节点不够）。
- **red**：有 primary 未分配 → 部分数据不可搜/不可写。

**口述：**
> yellow 不一定是灾难，单节点开发环境没副本就是 yellow。生产 yellow 要查是不是副本分配不上——节点挂了、磁盘水位、分配过滤规则。red 说明有主分片丢了，得立刻看 `_cluster/allocation/explain` 和 `_cat/shards`，是节点离线还是磁盘满了还是索引损坏。

---

## 7. 主分片所在节点挂了会怎样？

**知识点：**
- 有 replica：选举提升 replica 为新 primary，短暂 yellow，恢复后 green。
- 无 replica：该分片 red，对应数据不可服务，需从快照恢复或 reindex。
- 写入：在 primary 重新选举完成前，受影响分片可能拒绝写入。

**口述：**
> 只要副本够，主分片节点宕机会自动把某个副本提升为新主，集群会短暂 yellow，恢复后继续服务。如果没副本，那就是 red，只能依赖快照备份或从源库重建索引，所以生产至少 1 副本，关键索引 2 副本跨机架。

## 8. 分片分配失败常见原因？

**知识点：**
- 磁盘：`cluster.routing.allocation.disk.watermark`（low/high/flood）
- 规则：`allocation.require/_include/_exclude`、awareness 跨 AZ
- 容量：单节点分片数/磁盘比超限
- 新建索引：集群无足够 data 节点

**口述：**
> 分片 unassigned 我会先看 allocation explain API，它会直接告诉你是磁盘水位、过滤规则还是节点不够。磁盘 flood stage 会禁止分配甚至阻断写入，这时要扩容或删旧索引、调 ILM，而不是硬调副本。

---

## 9. 协调节点（coordinating）在查询里做什么？

**知识点：**
- scatter-gather：向各分片发子查询 → 合并 hits、聚合 partial 结果 → 排序截断返回。
- 深分页、大聚合在协调节点吃内存（`indices.breaker.*` 断路器保护）。
- `preference=_local` 可优先本地分片（缓存场景）。

**口述：**
> 用户发的搜索请求先到协调节点，它根据索引路由把查询扇出到所有相关分片，每个分片返回本地 TopN 或聚合中间结果，协调节点再合并排序。所以深分页和大 terms 聚合慢，往往是协调节点要处理的数据量太大，不只是某一个分片慢。

---

## 10. 跨集群复制（CCR）和快照（Snapshot）一句话？

**知识点：**
- Snapshot：备份到 S3/HDFS 等，灾难恢复、迁移。
- CCR：follower 索引异步复制 leader（容灾、就近读）。
- 恢复：restore snapshot 到新集群或同名索引（需改名）。

**口述：**
> 备份靠 snapshot 定期打到对象存储，恢复用 restore；异地多活或读就近可以用 CCR 做 follower 集群。面试讲容灾我会说：RPO/RTO 靠快照频率 + 恢复演练，而不是只备份配置不演练 restore。
