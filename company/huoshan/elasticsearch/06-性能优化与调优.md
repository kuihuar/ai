# 性能优化与调优

---

## 1. 写入性能优化手段？

**知识点：**
- **bulk**：批量写，建议 5~15MB/批或数千条，压测定拐点。
- `refresh_interval: -1` 导入期关闭自动 refresh，结束再 restore。
- 临时 `number_of_replicas: 0`（需容忍无副本），导入后恢复。
- 减少不必要的 `_source` 字段、关闭 norms、不需要评分的字段 `"index": false`。
- 客户端：并发 worker 数 ≈ 分片数倍数，重试指数退避。

**口述：**
> 大批量导入我会用 bulk API，控制每批字节数和并发度，导入期间把 refresh 调大或关掉、副本降为 0，写完统一 refresh 并恢复副本。mapping 提前建好避免动态映射，id 尽量外部生成保证幂等。整个过程要监控 rejected 和 bulk 失败重试队列。

---

## 2. 查询性能优化手段？

**知识点：**
- 条件放 `filter`；`size` 只取需要的字段（`_source` filtering）。
- 避免深分页、wildcard、script 排序。
- 合理分片与副本，读打 replica。
- **request cache**：分片级，仅 size=0 且 filter 可缓存查询。
- **query cache**：节点级，缓存 filter bitset（segment 不变才有效）。

**口述：**
> 查询优化第一条是 DSL 和 mapping 对不对，第二条才是硬件。列表查询只返回展示字段，过滤走 filter，分页用 search_after。热点查询如果聚合维度固定，可以 size 0 打 request cache。还要看重是不是某几个分片特别热，是的话考虑 routing 或拆索引。

## 3. refresh / flush / force merge 怎么选？

**知识点：**
| 操作 | 场景 | 风险 |
|------|------|------|
| refresh | 尽快可搜、导入后手动刷新 | 频繁 refresh 降写入吞吐 |
| flush | 定期落盘，translog 清 | 正常机制 |
| force merge | 只读历史索引合并为单 segment | 高 IO，阻塞风险，需维护窗口 |

**口述：**
> refresh 管「能不能搜到」，flush 管「落没落盘」。force merge 我只在索引只读、且要优化查询或释放空间时用，比如 ILM 进入 cold 之后，绝不在热写入索引上天天 force merge。

## 4. JVM heap 和操作系统缓存？

**知识点：**
- 官方建议 heap **不超过 32GB**（避免 compressed oops 失效）且不超过物理内存 50%。
- Lucene 依赖 **OS page cache** 做索引文件缓存，heap 过大反而挤占 cache。
- 监控：GC pause、old gen、heap 使用率、circuit breaker。

**口述：**
> ES 不是 heap 越大越好。大量索引数据靠操作系统页缓存，heap 主要放聚合、fielddata 等。一般 data 节点 31G 左右封顶，其余留给 OS cache。如果 old GC 频繁或 breaker 经常 trip，先查聚合和 fielddata，而不是无脑加内存。

## 5. 冷热温分层（hot-warm-cold-frozen）？

**知识点：**
- **hot**：SSD，读写频繁；**warm**：仍查询，可 shrink 减副本。
- **cold**：可 searchable snapshot；**frozen**：极低成本，查询慢。
- ILM 自动迁移节点属性 `node.attr.data: hot`。

**口述：**
> 日志和指标按时间分层：近 7 天 hot 节点 SSD 扛写入和查询，30 天内 warm，更老的数据 cold 或 frozen，成本下来还能查。关键是 ILM policy 和节点 attr 配好，避免老索引还占 hot 节点磁盘。

## 6. 如何避免 segment merge 打满 IO？

**知识点：**
- `index.merge.scheduler.max_thread_count`、限流写入。
- 减少单索引分片碎片；导入后统一 merge（维护窗）。
- 使用 **indexing pressure** 监控（7.x+）拒绝过载写入。

**口述：**
> merge 跟不上写入时，查询和写入都会抖。我会先看 indexing pressure 是否拒绝、磁盘 IO util 是否 100%，然后降 bulk 速率或临时扩节点。长期靠合理分片数和冷热分离，让热索引保持较小 segment 数量。

---

## 7. 副本数、读扩展和缓存命中？

**知识点：**
- 增加 replica → 读吞吐 ↑、存储 ↑、写入路径复制开销 ↑。
- 同一查询打不同 replica 可能 cache 不共享（request cache 分片级）。

**口述：**
> 读多写少可以多加副本分担查询，但写入也要复制多一份，所以不是副本越多越好。缓存方面，同样的 filter 查询在 segment 不变时能命中 bitset，索引有写入就会失效，所以缓存适合相对静态的过滤条件。

---

## 8. 向量检索（kNN）性能要点？

**知识点：**
- `dense_vector` + HNSW（`index: true`）。
- 参数 `m`、`ef_construction` 影响构建时间和召回。
- 查询 `num_candidates`、`k` 权衡延迟与精度；8.x 支持 filter + kNN 混合。

**口述：**
> 语义搜索会在 ES 里存 embedding，用 HNSW 索引做近似最近邻。调参时 m 和 ef 越大索引越大、构建越慢，但召回更好。线上要设合理的 k 和 num_candidates，并结合 metadata filter 缩小空间，否则全库向量扫很慢。
