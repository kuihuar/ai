# 场景题与架构口述（2~3 分钟）

---

## 1. ES + MySQL 数据一致性怎么保证？

**知识点：**
- 模式：**CDC**（Canal/Debezium 读 binlog）→ MQ → 消费写 ES；或业务双写（不推荐做主路径）。
- 一致性：**最终一致**；窗口内搜索可能旧数据。
- 幂等：以业务 `doc_id` 做 upsert；消费 offset 与版本号。
- 补偿：定时对账、全量 reindex、死信队列重试。

**口述（2 分钟）：**
> 我们不让应用直接双写 MySQL 和 ES，而是以 MySQL 为准。订单变更走 binlog，CDC 发到 Kafka，消费者按订单 ID 幂等更新 ES 文档。这样写路径解耦，ES 挂了也不影响交易。一致性是最终的，一般秒级延迟，搜索页可接受。为防止消息丢或乱序，消费者带版本号，旧版本丢弃；每晚对账抽样，发现不一致走补偿任务 reindex 该 ID。全量重建索引用 alias 切换到新索引，避免在线改 mapping。

**追问：**
- 删除怎么办？→ CDC 带 delete 事件，ES 用 delete API；或软删字段 filter。
- 消息重复？→ 幂等 upsert + 版本号。

## 2. 高并发搜索（十万/百万 QPS）架构怎么答？

**知识点：**
- 接入：CDN/网关缓存热点查询、限流、降级（只 filter 不搜全文）。
- ES：多分片多副本、协调节点水平扩展、热点索引拆分。
- 缓存：Redis 缓存搜索结果 key=query+filter hash；空结果短缓存防穿透。
- 查询：filter 化、size 控制、禁用深分页、异步 suggest。
- 容灾：多 AZ、副本跨机架、只读副本集群。

**口述：**
> 首先区分读多写少，搜索请求尽量无状态，前面加 Redis 缓存热门 query，TTL 几十秒。ES 侧保证索引分片合理、只读副本扛流量，协调节点可单独扩容。DSL 上条件全部 filter 化，禁止深分页和通配符。热点词单独治理，比如「手机」这种独立缓存或预计算。最后必须有降级：ES 超时返回缓存或简化结果，保护主站可用性。

## 3. 商品搜索相关性差，你怎么优化？

**口述：**
> 我会分三步。第一步看数据：标题是否分词合理、有没有用 keyword 搜 text。第二步召回：加同义词、品牌词词典、拼写纠错，必要时 ngram 补全部分匹配。第三步排序：用 function_score 叠加销量、点击率、库存、距离；业务规则如自营加权。每步用离线评测集算 NDCG，线上小流量 A/B，避免拍脑袋调 boost。

## 4. 日志平台（ELK）架构口述

**知识点：**
- Beats/Agent → Kafka（缓冲）→ Ingest → data stream → Kibana。
- ILM 控制保留；Frozen 降本。
- 慢查：集群级 index pattern，用 runtime field 要谨慎。

**口述：**
> 日志量最大的是写入，前面 Kafka 削峰，ingest pipeline 做字段裁剪和 geoip 解析，写入 data stream 绑 ILM 自动 rollover 和 30 天删除。查询在 Kibana 用时间范围必选，避免全集群扫。告警用 Elasticsearch Watcher 或外接 Prometheus/Alertmanager。

## 5. 为什么选 ES 不选 ClickHouse / Solr？

**口述：**
> 要全文和相关性排序、轻量聚合看板，ES 生态成熟。纯分析型超大宽表聚合、精确 SQL 报表更偏 ClickHouse。Solr 也可做搜索，但团队栈若已是 ELK 或云托管 ES，运维统一更重要。我会强调按场景选型，不是银弹。

## 6. 线上 ES 集群变慢，你的排查故事（STAR）

**口述模板：**
> **S**：大促后商品搜索 P99 从 200ms 到 2s。  
> **T**：定位是 ES 还是应用。  
> **A**：先看 APM 和 ES slowlog，发现某个 index 的 bool 查询带 leading wildcard；profile 显示 query 阶段占 80%。同时 `_cat/shards` 发现两个 primary 特别大。改 DSL 去掉 wildcard，category 改 filter；把历史索引 ILM 迁 cold；对超大分片索引做 reindex 均衡分片。  
> **R**：P99 回到 250ms，CPU 降 40%。  

（面试用真实数字替换更有说服力。）

## 7. 安全与多租户（加分）

**知识点：**
- X-Pack 安全：RBAC、API key、TLS、audit。
- 多租户：`routing` + 索引 per tenant 或 document level security。
- 敏感字段：不索引、加密存储在 MySQL only。

**口述：**
> SaaS 场景会给租户 ID 强制 filter，大租户独立索引隔离 noisy neighbor。敏感信息不进 ES 或只存 hash。生产必须开启认证 TLS，禁止 9200 裸奔。

---

## 8. 面试收尾：ES 不适合什么？

**口述：**
> ES 不适合强事务、频繁小字段更新、精确金融对账、复杂 JOIN。这些留在 MySQL/数仓。我的原则是 ES 做搜索和分析视图，权威数据永远在 OLTP，通过 CDC 同步，并接受近实时最终一致。
