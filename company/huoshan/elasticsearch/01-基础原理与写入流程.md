# ES 基础原理与写入流程

---

## 1. Elasticsearch 是什么？和 MySQL 怎么分工？

**知识点：**
- ES：分布式搜索/分析引擎，底层 Lucene，强项是全文检索、过滤、聚合、近实时分析。
- MySQL：ACID、关系约束、JOIN、强一致 OLTP。
- 常见架构：MySQL 为 Source of Truth，ES 为搜索视图（Search Index / Read Model）。

**口述：**
> ES 不是关系数据库的替代品，而是搜索和分析层。我们一般把 MySQL 当权威数据源，ES 当搜索索引，接受秒级以内的最终一致。选型上看，需要事务、强一致、复杂关联查 MySQL；需要全文搜、多维筛选、统计看板、日志分析就上 ES。

**追问：**
- ES 能代替 MySQL 吗？→ 不能，无跨文档事务、更新成本高、不适合金融账本类强一致。

## 2. 倒排索引是什么？为什么比全表扫描快？

**知识点：**
- 正排：文档 ID → 字段内容；倒排：词项（term）→ 文档 ID 列表（posting list）。
- Lucene 段（segment）内：词典（Dictionary）+ 倒排表 + 压缩（如 FOR、PForDelta）。
- 查询：先查词典定位 term，再合并 posting list（AND/OR/NOT）。

**口述：**
> 倒排索引本质是「词到文档列表」的映射。用户搜「北京 天气」，先把查询分词得到 term，再在倒排表里找包含这些 term 的文档集合，做交集或并集，而不是逐行扫全表。配合跳表、压缩和按段组织，能在海量文档里快速定位候选集，这是 ES 全文搜索快的根本原因。

**追问：**
- posting list 很长怎么办？→ 跳表加速合并、位图（Roaring）用于稠密场景、按段剪枝。

## 3. 正排索引（doc values）是干什么的？

**知识点：**
- 列式存储在磁盘，用于排序、聚合、脚本访问字段，不走倒排。
- `text` 默认不建 doc values（或不可用），排序/聚合要用 `keyword` 子字段。
- 高基数字段聚合会构建 global ordinals，内存开销大。

**口述：**
> 倒排解决「按词找文档」，正排（doc values）解决「按文档读字段值」，主要服务排序和聚合。所以面试里常说：要聚合、排序的字段用 keyword 或专门子字段，别直接对 text 做 terms 聚合，否则又慢又占内存。

## 4. 为什么叫近实时（NRT）？refresh / flush 区别？

**知识点：**
- 写入：协调节点 → routing 算分片 → primary 写内存 index buffer + 写 translog。
- **refresh**（默认 1s）：buffer 生成新 segment，对搜索可见；未持久化到磁盘主数据。
- **flush**：segment 落盘，清空 translog（先 fsync translog 再 commit）。
- 可调 `index.refresh_interval`（导入可设 `-1` 关闭自动 refresh）。

**口述：**
> ES 不是写入立即可搜。数据先进内存 buffer 和 translog，refresh 周期性地把 buffer 刷成新 segment，这时搜索才能看到。真正持久化要靠 flush 把 segment 写到磁盘并处理 translog。所以叫近实时，默认大约 1 秒延迟。大批量导入时我们会临时调大 refresh 间隔甚至关掉，写完再手动 refresh，换写入吞吐。

**追问：**
- translog 作用？→ 宕机恢复未 flush 的写入；类似 WAL。

## 5. 一条写请求的完整路径？

**知识点：**
- `routing` 默认 `_id`，公式：`shard = hash(routing) % num_primary_shards`。
- 写 primary → 并行复制 replica → 满足 `wait_for_active_shards` 后返回。
- 版本：内部 `_seq_no` + `_primary_term` 做乐观并发（`if_seq_no` / `if_primary_term`）。

**口述：**
> 客户端发到协调节点，根据 routing 定位 primary shard，先写 primary 的 buffer 和 translog，再转发到各 replica 副本。副本都 ack 后（或达到配置的最小活跃副本数）才给客户端成功。分片 ID 由 routing 和主分片数决定，所以主分片数创建后不能随便改，否则同一文档会路由到错误分片。

## 6. Segment 是什么？merge 为什么影响性能？

**知识点：**
- 每个 segment 是独立的 Lucene 索引，只读；更新/删除是标记删除 + 新文档写入新 segment。
- 后台 **merge** 把小 segment 合成大 segment，回收删除空间。
- segment 过多：文件句柄、内存、查询要查多个 segment 再合并结果。

**口述：**
> Lucene 用只读 segment 组织数据，更新不是原地改，而是写新 segment 并标记旧文档删除。久了 segment 很多，查询要跨段合并，后台还要 merge，占 CPU 和磁盘 IO。写入高峰时 merge 压力大，会出现延迟抖动，所以生产会控制 bulk 速率、冷热分离，历史只读索引才考虑 force merge。

## 7. `_id`、`_source`、`_version` 分别是什么？

**知识点：**
- `_id`：文档唯一标识（可自定义，不指定则自动生成）。
- `_source`：原始 JSON 存储，默认开启；关闭可省空间但无法 reindex 部分字段。
- `_version` 已弱化，并发用 `_seq_no` / `_primary_term`。

**口述：**
> `_id` 是业务或系统给的文档主键，影响 routing。`_source` 存原始文档，搜索命中后展示、reindex 都靠它。如果字段特别多、只关心聚合，可以对部分字段 `"enabled": false` 或关掉 `_source`，但要清楚后续无法从 ES 还原完整文档。

## 8. ES 与 Solr、OpenSearch 怎么一句话对比？

**知识点：**
- Solr：传统单体 + SolrCloud，配置偏 XML，生态成熟。
- OpenSearch：AWS 分支，API 与 ES 7.x 高度兼容。
- ES：生态（Kibana、Beats、ELK）、云原生、企业功能（安全、ML）完整。

**口述：**
> 面试如果被问竞品，我会说 ES 的优势在分布式运维成熟度、ELK 全家桶和云厂商托管方案；Solr 在纯搜索定制也常见；OpenSearch 适合 AWS 体系或开源协议诉求。原理层面都是 Lucene 系，倒排和分片思路相通。
