# Go + Python 混合后端：面试口述题（基于 README 准备建议）

适用目标：围绕“准备 1~2 个 Go + Python 混合后端项目案例，重点讲架构分层与接口设计”进行口述训练。  
建议答题结构：**背景 -> 目标 -> 方案 -> 权衡 -> 结果**。

---

## 1) 为什么你的项目要同时使用 Go 和 Python？如何分工？

**口述参考（60~90 秒）：**  
我们项目是典型的“在线服务 + 算法工作流”场景。Go 主要承接高并发 API 和核心业务编排，因为它启动快、内存可控、并发模型稳定；Python 负责模型推理、数据处理和特征加工，因为算法生态更成熟。边界上我们要求“业务入口不直连模型细节”，所以 Go 通过 RPC 调 Python 推理服务，接口做强约束，避免语言耦合。这样分工的收益是：在线链路稳定性由 Go 兜底，模型迭代速度由 Python 保证。代价是跨语言调用和协议维护成本上升，所以我们统一 protobuf + 版本管理，减少协作摩擦。

**追问点：**
- 为什么不全用 Go？
- 为什么不全用 Python？
- 出问题先查 Go 还是 Python？

---

## 2) 你怎么设计 Go 与 Python 之间的接口？

**口述参考（60~90 秒）：**  
我会先从业务对象建模，而不是从函数签名开始。我们统一 protobuf 定义 Request/Response，强制携带 trace_id、tenant_id、request_version。接口层分三类：同步推理、异步任务提交、批量处理。同步接口强调超时和降级，异步接口强调幂等和可追踪。版本策略是“向后兼容字段新增，不做破坏性删除”，上线时 Go 和 Python 双端兼容一个版本窗口。这样做可以把“语言差异”收敛到协议层，避免接口含糊造成线上事故。

**追问点：**
- 字段变更如何灰度？
- 错误码如何统一？
- 如何避免 JSON 漂移问题？

---

## 3) 混合架构下的分层设计是怎样的？

**口述参考（60~90 秒）：**  
我们分四层：接入层、编排层、能力层、存储层。接入层是 Go API 网关，做鉴权、限流、参数校验。编排层由 Go 服务实现，负责业务流程和策略路由。能力层是 Python 模型服务和数据处理服务，专注算法能力。存储层包括 MySQL、Redis、Elasticsearch，分别承接权威数据、热点缓存和检索。分层原则是“跨层只走接口，不穿透依赖”，这样后续替换模型或缓存方案不会影响 API 层。

**追问点：**
- 哪层最容易变？
- 哪层最需要稳定？
- 你如何控制跨层调用链长度？

## 4) 如果 Python 推理服务抖动，Go 侧如何兜底？

**口述参考（60~90 秒）：**  
Go 侧我会做四级兜底：第一层是超时控制和重试上限，避免请求堆积；第二层是熔断和隔离仓，防止故障扩散；第三层是降级策略，比如返回缓存结果、规则结果或简化版本；第四层是异步补偿，把失败请求写队列重放。监控上重点看超时率、P95/P99、错误码分布和下游依赖健康。核心目标不是“完全不失败”，而是“失败可控且业务可用”。

**追问点：**
- 重试会不会放大雪崩？
- 如何定义降级可接受边界？
- 熔断恢复策略是什么？

## 5) 你如何保证跨语言链路的可观测性？

**口述参考（60~90 秒）：**  
我们把 trace_id 作为强制透传字段，HTTP/gRPC/MQ 全链路传递。日志统一结构化输出，至少包含 trace_id、span_id、tenant、接口名、耗时、错误码。指标层用 RED（请求率、错误率、延迟）和 USE（资源利用）双视角。排障流程是先看告警面，再通过 trace 定位慢点在 Go 编排还是 Python 推理，最后结合日志定位到具体模型版本或输入分布异常。这样可以把“语言切换导致的排障盲区”降到最低。

**追问点：**
- trace 采样率怎么定？
- 高 QPS 下日志成本怎么控？
- 如何做多租户观测隔离？

## 6) 你如何做性能优化？先优化哪一端？

**口述参考（60~90 秒）：**  
先通过压测和 profile 找瓶颈，不先入为主。若瓶颈在 Go，常见是序列化、锁竞争、下游等待，我会做连接池优化、批量化、缓存与并发控制。若瓶颈在 Python，常见是模型加载、GIL 影响、向量化不足，我会做多进程 worker、预热、批推理和特征缓存。最终指标要落在业务 SLA，比如 P95 从 800ms 降到 300ms，而不只看单机 QPS。优化结束后保留压测基线，避免回归。

**追问点：**
- GIL 对你的场景影响大吗？
- 为什么不用异步 Python 全链路？
- 如何评估优化收益真实性？

## 7) 混合服务怎么做发布和回滚？

**口述参考（60~90 秒）：**  
发布上我们做双维度灰度：流量灰度和版本兼容灰度。先升级 Python 能力服务保持协议兼容，再灰度 Go 编排层启用新特性。回滚优先走开关和路由回切，不依赖紧急发版。CI/CD 阶段强制契约测试和冒烟测试，保证跨语言接口不破坏。发布看板实时观测错误率和时延，触发阈值自动停止扩量。核心是把“多服务、多语言、多版本”变成可控的发布流程。

**追问点：**
- 如何做契约测试？
- 版本不兼容时怎么止损？
- 回滚为什么先回切流量？

## 8) 你如何处理数据一致性问题（Go 写库 + Python 异步消费）？

**口述参考（60~90 秒）：**  
我们采用最终一致模型。权威写入先落 MySQL，再发事件给 Python 异步处理，避免分布式事务。为了保证可恢复，消息必须幂等，消费端按业务主键去重，失败进重试队列和死信队列。对外查询如果需要强一致，就读 MySQL；搜索和报表允许秒级延迟读 ES。这个设计的关键是明确一致性等级，给业务方透明预期，而不是追求不必要的强一致。

**追问点：**
- 如何处理重复消息？
- 如何处理乱序消息？
- 什么时候必须强一致？

## 9) 你怎么描述一个真实的线上问题排查案例？

**口述参考（60~90 秒）：**  
我通常按 STAR 表达。S：上线后生成接口超时率从 1% 升到 12%。T：定位是 Go 编排问题还是 Python 推理问题。A：通过 trace 发现 Python 下游耗时飙升，进一步看日志定位到模型未命中预热，触发了频繁冷加载；临时措施是 Go 侧降级到缓存模板，Python 侧紧急预热并限制并发。R：30 分钟内超时率恢复到 2% 以下，后续补了发布前预热检查和容量压测。这样回答既体现技术判断，也体现工程闭环。

**追问点：**
- 为什么不是数据库问题？
- 如何防止再次发生？
- 告警阈值如何设置？

## 10) 如果让你重做这个项目，架构上会改什么？

**口述参考（60~90 秒）：**  
我会更早做“能力网关化”和“接口契约平台化”。第一，把 Python 能力统一注册到能力网关，Go 编排层只面向标准能力目录，减少点对点依赖。第二，接口 schema 和版本生命周期纳入平台治理，做到变更可审计。第三，把离线评测和线上 A/B 指标接通，让模型迭代和业务指标同频。这三点能显著降低跨团队协作成本，也更适合后续多 Agent 扩展。

**追问点：**
- 为什么此前没这么做？
- 改造优先级怎么排？
- 如何量化改造 ROI？

## 快速练习法（建议）

- 每天挑 3 题，按“90 秒主答 + 30 秒追问”录音复盘。
- 主答必须说出 1 个架构决策 + 1 个权衡点 + 1 个结果指标。
- 每题准备一个“失败经验”，面试官更容易认可真实性。
