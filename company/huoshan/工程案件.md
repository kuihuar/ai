## 🎯 核心考点一：Go + Python 混合后端项目案例

### 案例 1：高性能高并发物联网（IoT）安全数据清洗与策略分发平台
* **业务背景**：系统需要接收来自数十万台企业终端（Agent）的高频行为日志上报（秒级千万级数据流），进行实时行为审计、风控规则判定，并支持运营/安全人员在 Web 后台动态修改下发防御策略。
* **混合架构选型逻辑**：
    * **Go**：负责流量入口层。承载数十万长连接、二进制私有协议（或 gRPC）的解密验证、高并发流式限流、对象池（`sync.Pool`）零拷贝数据清洗。
    * **Python**：负责规则计算与 AI/流式风控分析层。安全算法迭代快，利用 Python 丰富的生态（数据分析、复杂规则图解释器、策略动态热加载）实现风控判定，随后将决策下发回 Go 网关执行。

#### 1.1 架构分层设计
系统整体采用**六边形架构（Ports and Adapters）**演进的洋葱整洁架构，严格将传输协议、业务领域与外部依赖隔离。
* **流量入口层（Go - GateWay / Transport）**：基于原生 Epoll 网络模型封装（或高性能微服务框架）。负责解包、防篡改校验。不涉及任何业务逻辑，将二进制流转换为结构化结构体。
* **缓冲编排层（Go - RuleChain / Pipeline）**：参考 `RuleGo` 的链式设计，采用高效的内存 Ring Buffer。处理高性能限流、基础白名单过滤。对需要重度业务计算的数据，通过 gRPC 或者是 Kafka 消息队列路由给 Python 侧。
* **业务领域决策层（Python - RuleEngine / Domain）**：基于现代 JSON 决策图（如 `GoRules` 的底层思想）进行策略匹配。这里只处理纯粹的事实（Facts）与规则（Rules）运算。
* **基础设施层（Go/Python - Repository）**：Go 侧负责秒级 Bulk 写入 Elasticsearch 和 Kafka；Python 侧维护配置中心的热加载。

#### 1.2 接口设计（跨语言通信与依赖倒置）
为了彻底解决 Go 与 Python 之间的调用耦合与性能损耗，放弃低效的 HTTP/JSON，全面采用 **gRPC + Protobuf**，实现接口契约先行（Schema First）。

* **API 契约定义（`action_audit.proto`）**：
```protobuf
syntax = "proto3";
package security.audit.v1;

// 策略决策服务（Python 端实现，Go 端调用）
service PolicyEngineService {
    rpc EvaluateBehavior (EvaluateRequest) returns (EvaluateResponse);
}

message EvaluateRequest {
    string trace_id = 1;
    int64 tenant_id = 2;
    string agent_id = 3;
    string behavior_type = 4;
    bytes raw_payload = 5; // 原始加密行为报文，延迟解析
}

message EvaluateResponse {
    enum Action {
        ALLOW = 0;
        BLOCK = 1;
        CHALLENGE = 2; // 触发二次验证
    }
    Action action = 1;
    string rule_id = 2;
    string message = 3;
}

#### 1.3 模拟面试追问：
1. **问**：Go 调用 Python gRPC 服务时，如果 Python 侧因为 GIL 锁或计算密集导致响应变慢，如何防止 Go 端的 Goroutine 雪崩？
   * **答**：在 Go 端实现**依赖倒置**与**熔断隔离模式**。使用 `context.WithTimeout` 严格限制 gRPC 调用超时为 200ms。引入 `gobreaker` 断路器，一旦 Python 侧慢请求比例超过 35%，立刻触发熔断。业务降级进入 Go 本地轻量级白名单兜底逻辑，直接 Fail-Fast，释放协程栈内存。
2. **问**：在混合架构中，如何保证两套语言系统之间分布式链路追踪（Tracing）的连贯性？
   * **答**：基于 **OpenTelemetry** 标准。Go 网关生成 `trace_id` 后，通过 gRPC 的 `metadata`（或者是 Kafka 的 Header）进行隐式传递。Python 端通过拦截器（Interceptor）提取 Context，使得一条安全审计请求从终端上报到 Go、再到 Python、最后写入 ES 的全链路日志拥有唯一的上下文 ID。

## 🤖 核心考点二：LLM 能力工程化落地案例

### 案例 2：企业级智能运维与全离线知识库（RAG）系统落地
* **业务背景**：为政企内部开发一套智能资产审计与排障辅助助手。由于安全合规限制，必须在私有化环境部署，前端并发量大，要求召回准确率高于 90%，杜绝幻觉（Hallucination）。

#### 2.1 数据链路设计（Data Pipeline）
构建高可用的自动化数据清洗与向量化资产管道（离线 + 在线同步）：
* **数据清洗与切片（ETL）**：Python 异步任务（Celery）监控 Wiki、技术文档、产品说明（如天擎配置手册）。采用 Markdown 规范化解析器，不仅按照 Token 长度（512）切片，还采用 **Layout-aware（布局感知）** 策略，保持标题层级与表格结构的完整。
* **富集与元数据打标**：对切片（Chunk）进行特征富集，通过传统 NLP 提取关键词，并打上 `tenant_id`、`os_platform`、`doc_version` 等强元数据标签，防止在线检索时跨租户数据越权。
* **向量化与存储**：调用本地 Embedding 模型生成向量，批量（Batch）写入 Milvus 向量数据库，同时将文本与关键词同步写入 Elasticsearch（用于两路召回）。

#### 2.2 召回策略（Retrieval Strategy）
单路向量检索在长尾词和特定错误码（如 `0x00000050`）上召回极差。项目采用 **混合检索（Hybrid Search） + 重排（Reranking）** 架构：
1. **密集检索（Dense Retrieval）**：Milvus 向量库，利用 HNSW 索引做语义近似度检索，召回 Top 30。
2. **稀疏检索（Sparse Retrieval）**：Elasticsearch，基于 BM25 算法对用户输入的精准错误码、产品型号进行文本匹配，召回 Top 30。
3. **元数据硬过滤（Metadata Filtering）**：在检索阶段，强行带入当前用户的身份标签，通过 Milvus 的布尔表达式过滤，确保数据物理安全隔离。
4. **混合重排（Rerank）**：将两路召回的 60 个 Chunk 汇聚，调用本地 `bge-reranker-large` 模型，计算 Query 与 Chunk 的真实相关性得分，最终只取 Top 5 送入 LLM 的 Context Window。

#### 2.3 效果评估（Evaluation）
上线前与日常迭代引入 **RAG Triad（RAG三元组）** 自动化评估框架，配合人工 Golden Dataset 校验：
* **Context Relevance（上下文相关性）**：评估召回的 Top 5 文本是否真的包含回答问题所需的信息，用于惩罚垃圾召回，优化重排模型。
* **Groundedness（真实性/忠实度）**：检查 LLM 输出的每一句话，是否都能在 Context 中找到原文依据，严厉监控“幻觉”指标。
* **Answer Relevance（回答相关性）**：评估最终输出是否切中用户提问，通过另一台大型 LLM 进行打分评估。

#### 2.4 模拟面试追问：
1. **问**：当多个高并发请求同时到达，LLM 推理速度慢导致流式响应（Streaming）卡顿，你在后端工程上做了哪些优化？
   * **答**：首先，在 Go 服务端网关层引入 **Event-Stream（SSE，Server-Sent Events）** 协议，配合 `gin` 框架的流式渲染，让用户感知延迟降低到首字 500ms 内。其次，在 Python 推理层前置引入 **vLLM** 框架，开启 **PagedAttention（分页注意力机制）** 与 **Continuous Batching（连续批处理）**，将单卡吞吐量提升了 3.5倍，极大缓解了排队等待问题。

## 🛠️ 核心考点三：线上性能或稳定性问题排障案例

### 案例 3：线上 Go 微服务高并发下内存暴涨、频繁 OOM 触发系统雪崩
* **业务背景**：某个承载策略路由的 Go/Gin 服务，在一次安全攻防演练期间，由于日志量暴增 10 倍，导致线上 Pod 频繁发生 OOM（Out of Memory）重启，监控曲线呈现锯齿状，触发系统整体雪崩。

#### 3.1 问题定位路径（Root Cause Analysis）
1. **第一步：紧急止血与指标观测**：
   观察 Prometheus 监控，发现每次 Pod 重启前，Go 进程的 `go_memstats_heap_alloc_bytes`（堆内存分配）持续陡峭上升，系统 GC 占用了高达 40% 的 CPU（GC Pacing）。排除了系统层内存泄露（Memory Leak），确认是**瞬时高并发带来的高频对象内存分配速度远超 GC 回收速度**。
2. **第二步：火焰图排查（pprof）**：
   由于是在线环境，通过预留的 `net/http/pprof` 端口，在服务不重启的状态下抓取了 30 秒的内存 Profile。
   ```bash
   go tool pprof -http=:8080 http://localhost:6060/debug/pprof/alloc_space
